BasicPlus — El lenguaje JC

JC es BasicPlus escrito con la sintaxis de Java y C#. Este volumen cuenta el lenguaje: cómo se escribe cada cosa en JC, qué es en BP y en qué se diferencian. Lo demás se comparte con BP —la biblioteca estándar, la interfaz gráfica, las bases de datos, el IDE y las placas— y sus volúmenes valen tal cual para un programa en JC (§19).

1. Qué es JC

1.1 El mismo lenguaje, otra ropa

JC (de Java y C#) es BasicPlus con llaves, punto y coma y el tipo delante del nombre. No es otro lenguaje: es el mismo con otra sintaxis.

  • El compilador es el mismo. basicplus-frontend.jar lee los .bp y los .jc, elige el lector por la extensión y los lleva al mismo árbol; de ahí en adelante, todo es común.
  • El bytecode es el mismo. El mismo programa, escrito en BP o en JC, da el mismo .mod, byte a byte. Sólo cambia el .dbg, que cita su fuente y sus líneas.
  • Las VMs no se enteran. Un programa en JC corre igual en el PC y en las placas, se depura igual y usa las mismas librerías.

Y por eso JC no es Java ni C#: lo que BP no tiene —las lambdas, los struct, los genéricos propios con <T>…— JC tampoco lo tiene, y algunas cosas se comportan como en BP aunque se escriban como en C#. Están juntas en §17.

1.2 ¿BP o JC?

Es cuestión de gusto: el resultado es el mismo, con la misma velocidad y las mismas librerías. JC, si vienes de Java, de C# o de C; BP, si prefieres bloques que se cierran con end y sentencias sin ;.

  • Se mezclan. Un módulo en JC importa módulos en BP, y la biblioteca estándar está escrita en BP (§5.4).
  • Se traducen. El compilador lleva un fuente de un lenguaje al otro, y el IDE también, con una orden del menú (§18.3).
  • Los otros volúmenes están en BP. Sus ejemplos se leen en JC con las tablas de este volumen, o se traducen; §19 cuenta cómo leer una firma de BP.

2. Un primer programa

2.1 Hola, en los dos

BP

module Hola
  function main(arg: string := "mundo")
    print "hola, "; arg
  end main
end Hola

JC

module Hola
{
   function void main(string arg = "mundo")
   {
      println("hola, ", arg);
   }
}

El módulo va entre llaves, y cada sentencia acaba en ;. El tipo va delante del nombre (string arg), y una función que no devuelve nada es void. El valor por defecto de un parámetro se escribe con =. Y println escribe sus piezas, una tras otra, y salta de línea.

2.2 Compilar y ejecutar

Las mismas órdenes que para un .bp (referencia §16):

java -jar basicplus-frontend.jar Hola.jc --compile out --backend=mivm
java -jar bpgenvm.jar out/Hola.mod
bpgenvm-c out/Hola.mod "a todos"
hola, mundo
hola, a todos

El segundo argumento de la VM es el de main; sin él, vale su valor por defecto. En el IDE, se abre el .jc y se ejecuta como cualquier fuente (§18.4).

2.3 print y println

Es lo primero que se nota al pasar de BP a JC. El print de BP salta de línea al final, y la coma pone un espacio entre las piezas. El de JC, no:

  • print(a, b); escribe las piezas una tras otra, sin nada entre ellas y sin saltar de línea. Es el print a; b; de BP.
  • println(a, b); hace lo mismo y salta de línea al final. Es el print a; b de BP.
  • println(); es sólo el salto, el print vacío de BP.

BP

module Piezas
  function main()
    var n: integer := 3
    print "n = ";
    print n;
    print ", y sigue en la misma línea"
    print "a"; "b"; 1 + 2
    print "a", "b"
    print
    print "fin"
  end main
end Piezas

  • Un "\n" dentro de una cadena es un carácter más: no cierra la línea. La línea sale entera —también con varios hilos escribiendo a la vez— cuando la cierra un println, o al acabar el hilo. Para que cada línea salga en su momento, println.
  • Las piezas se calculan en orden, y van entrando en la línea. Si una lanza una excepción, lo de antes ya está escrito y sale con lo siguiente que se escriba: para no mezclarlo, calcula antes lo que puede fallar.
  • print y println son palabras reservadas de JC, no funciones de una librería.

3. Un programa entero, en BP y en JC

El mismo programa en los dos lenguajes. Es el ejemplo con el que se decidió la sintaxis de JC, y toca casi todo lo básico: constantes, una variable y una property del módulo, un enum, una tupla, un parámetro con valor por defecto, una función inline, if, for, foreach, do, try y print. Primero en BP: 

module Ejemplo
  import Collections

  public const MAX: integer := 10
  const PI := 3.5
  var cuenta: integer := 0
  public property nivel: integer := 1

  public enum Color
    Rojo
    Verde := 5
  end Color

  function par(): (integer, string)
    return (1, "uno")
  end par

  public function sumar(a: integer, b: integer := 1): integer
    return a + b
  end sumar

  public function codigo(s: string, i: integer): integer
    inline CALL_BUILTIN 48
  end codigo

  public function main()
    var n: integer
    var s: string
    var l: List := List()
    { n, s } := par()
    if n > 0 and not (s == "") then print "si"
    for i := 1 to MAX step 2 do
      cuenta += i
    next
    for x in [1, 2, 3] do print x
    do
      n -= 1
    loop n > 0
    try
      throw RuntimeError("fallo")
    catch e: RuntimeError
      print e.msg
    endtry
    print "cuenta: "; cuenta; " pi: "; PI
  end main
end Ejemplo

Y en JC:

      catch (RuntimeError e)

Lo que enseña la comparación:

  • El tipo, siempre delante: en las variables, los parámetros, las constantes y el retorno (function int sumar(…)). Una constante de BP puede no llevarlo (const PI := 3.5); en JC, sí.
  • Los reales, como en C#: en JC, 3.5 es un double, y el float lleva su f, 3.5f. En BP es al revés: 3.5 es un float, y 3.5d, un double.
  • Lo que construye lleva new: el List() de BP es new List().
  • La property corta de BP es la automática de C#, { get; set; }.
  • El desempaquetado { n, s } := par() es (n, s) = par();.
  • Los operadores de palabra son los de C: and, or y not son &&, || y !.
  • El for, el do y el catch, con la ropa de C#: for (int i = 1; i <= MAX; i += 2), do { … } while (n > 0); y catch (RuntimeError e).
  • El salto de línea que el print de BP pone solo es el println de JC.

4. Lo básico

  • Las palabras reservadas distinguen mayúsculas: if, no If. En BP es al revés: IF y if son la misma palabra. Los nombres distinguen mayúsculas en los dos: total y Total son dos nombres.
  • Cada sentencia y cada declaración acaba en ;, y los saltos de línea no cuentan: una sentencia puede ocupar varias líneas.
  • Los bloques van entre llaves. Una llave suelta, sin el if, el bucle o la función a la que pertenece, es un error: «un bloque suelto». Con una sola sentencia, las llaves de un if, un while, un do, un for o un foreach se pueden omitir (§8.1).
  • Los comentarios: // hasta el final de la línea, como en BP, y además /* … */, que puede ocupar varias líneas.
  • Los nombres, como en BP: una letra o _, y después letras, dígitos o _, hasta 63 caracteres. Los que empiezan por __ son del sistema.
/* Un comentario
   de varias líneas */
int total = 0;            // y uno de línea
total = total
      + 1;                  // una sentencia en dos líneas

5. Módulos e import

5.1 El módulo

Un fichero es un módulo, como en BP: module Nombre { … }. Dentro van, primero, los import, y después las definiciones —constantes, variables, properties, funciones, clases, interfaces y enums— en cualquier orden. Lo que no es public es privado del módulo. 

module Medidor
{
   public const int MAXIMO = 100;
   int lecturas = 0;                     // privada del módulo
   public int ultima { get; set; }          // la ven los que importan Medidor

   public function void apunta(int v)
   {
      lecturas++;
      ultima = v;
      if (ultima > MAXIMO) println("¡pasa de ", MAXIMO, "!");
   }

   function void main()
   {
      apunta(42);
      apunta(120);
      println(lecturas, " lecturas, la última ", ultima);
   }
}
¡pasa de 100!
2 lecturas, la última 120

Una variable del módulo no puede ser public (es un error): lo que se comparte con otros módulos es una property, como ultima (manual §9.5). Con library "com.ejemplo"; delante de module, el .mod se llama com.ejemplo.Medidor.mod (manual §10.1).

5.2 main y la función de arranque

El programa empieza en function void main() del módulo raíz, o en main(string arg) si recibe un argumento (Main también vale). Y una función void sin parámetros que se llama como el módulo es su función de arranque: corre al cargarlo, tras las de los módulos que importa y antes de main. 

module Arranque
{
   int veces = 0;

   function void Arranque()
   {
      veces = 1;
      println("[init] cargado");
   }

   function void main(string arg = "defecto")
   {
      println("main con '", arg, "', veces = ", veces);
   }
}
[init] cargado
main con 'defecto', veces = 1

Con bpgenvm-c Arranque.mod hola, la segunda línea dice main con 'hola'. Lo demás del argumento —su tope de 127 bytes, el autorun, la consola del IDE— es lo de BP (manual §10.2).

5.4 Importar tus módulos

Un módulo en JC importa los de BP como cualquier otro: si el .bp está junto a él, el compilador lo compila también. Para importar otro módulo en JC, hoy hay una condición: el compilador busca el fuente de un import como .bp, así que un .jc importado se compila antes, y su .mod, junto al que importa o en la carpeta de salida, es lo que se encuentra. En un proyecto, se listan en sources, el importado primero (§18.2). 

module Utiles
{
   public const int VECES = 3;

   public function string repite(string s, int n = 3)
   {
      string r = "";
      for (int i = 1; i <= n; i++) r += s;
      return r;
   }
}
module Viejo
  public function doble(n: integer): integer
    return n * 2
  end doble
end Viejo
module Programa
{
   import Utiles;        // en JC: compilado antes
   import Viejo;         // en BP: el compilador encuentra Viejo.bp

   function void main()
   {
      println(Utiles.repite("ja"));
      println(Viejo.doble(21));
   }
}

java -jar basicplus-frontend.jar Programa.jc --compile out --backend=mivm

Sin compilar antes Utiles.jc, el compilador lo dice: «no se localizó .bp ni .bpi para import 'Utiles'», y después, que Utiles no se conoce. Un valor por defecto es un literal, como en BP: int n = VECES no vale, aunque VECES sea una constante.

6.5 Cadenas y null

Una cadena de JC es la de BP: texto UTF-8 que no cambia. Lo que espera quien viene de Java o de C#:

  • == compara el texto, como en C# (en Java compararía las referencias), y <, >… comparan el orden alfabético, por punto de código.
  • + concatena, y convierte a texto los números, los enums (su número) y los objetos (su toString()).
  • Una cadena no tiene métodos. Se usan las funciones de Core, que se ven sin importar nada: len(s), upper(s), substring(s, desde, hasta), indexOf(s, t), split(s, sep), replace, contains, startsWith, charAt, charCodeAt, parseInt… (la lista, en la referencia §13.1). Para ir juntando texto, StringBuilder.
  • No se indexa: s[i] no vale; charAt(s, i) da el carácter, como cadena, y charCodeAt(s, i), su código.
module Textos
{
   function void main()
   {

6.7 Enums

Como en C#: enum Color { Rojo, Verde = 5, Azul }, con una coma al final si se quiere. Es el enum … end de BP. Los valores se numeran desde 0, y uno escrito es un entero sin signo; las expresiones de C# (1 << 3, -1) y el tipo de debajo (enum Color : byte) no están.

7.4 Conversiones e is

Como en C#: (T) x. En BP, crear, llamar y convertir se escriben igual —Perro(x)— y decide el compilador; en JC cada cosa tiene su forma: new Perro(x) crea, (Perro) x convierte y f(x) llama.

  • Entre números: (int) d trunca hacia cero; (byte), (sbyte), (short) y (ushort) miran el rango al ejecutar y, si no cabe, lanzan un ArithmeticError; (long), (float) y (double) ensanchan. De un tipo pequeño a uno grande no hace falta escribirla: long l = i; vale.
  • Entre clases: (Perro) a baja desde un antepasado o desde Object, y si el objeto no es un Perro lanza un CastError. Lo que ya es un Perro se queda como está. Dos clases sin parentesco no se convierten: es un error de compilación.
  • x is Perro dice si el objeto es de esa clase o interfaz, o de una hija; también con el módulo delante, x is Lib.Perro. Lo demás del is de C# (x is Perro p, x is null) no está: para null, x == null.
  • Un paréntesis o una conversión, con la regla de C#: es una conversión si entre los paréntesis hay un tipo del lenguaje ((int)…), o si hay un nombre y tras el ) viene un nombre, un literal, una palabra reservada (new, this…), un ( o un !.   • Herencia simple: una clase base, y las interfaces que quiera (§11). Una clase sin base desciende de Object.
  • Todo método es virtual salvo los private: no hay virtual ni override, y un método de la hija con la misma firma sustituye al del padre. Para dejarlo escrito, la anotación @override{} (§11). Un método final no se puede redefinir, y una clase final (public final class Base) no se puede extender, tampoco desde otro módulo.
  • No hay clases dentro de clases, abstract, struct ni clases static. Para un tipo sin código, una interfaz.

11. Interfaces

Una clase hereda de una sola clase e implementa las interfaces que quiera. Una interfaz dice qué métodos y qué properties tiene un tipo, sin código, y puede heredar de varias. 

module Formas
{
   public interface Forma
   {
      function double area();
      function string nombre();
   }

   public interface Poligono : Forma
   {
      function int lados();
   }

   public interface Etiquetado
   {
      string etiqueta { get; set; }
   }

   public class Figura
   {
      public function string nombre()
      {
         return "figura";
      }
   }

   public class Cuadrado : Figura, Poligono, Etiquetado
   {
      private double lado;

      @implement{ Etiquetado }
      public string etiqueta { get; set; }

      public function Cuadrado(double l)
      {
         this.lado = l;
      }

      @implement{ Poligono }
      public function double area()
      {
         return this.lado * this.lado;
      }

      @implement{ Poligono }
      public function int lados()
      {
         return 4;
      }

      @implement{ Poligono }
      @override{}
      public function string nombre()
      {
         return "cuadrado";
      }
   }

   function void main()
   {
      Forma f = new Cuadrado(2.0);
      println(f.nombre(), " ", f.area());
      Poligono p = (Poligono) f;
      println(p.lados(), " ", f is Etiquetado);
      Etiquetado e = (Etiquetado) f;
      e.etiqueta = "cuadrado de 2";
      println(e.etiqueta);
   }
}

  • Lo que lleva una interfaz: métodos, sólo su firma y con su function (function double area();), y properties automáticas (string etiqueta { get; set; }). Todo es público, sin escribirlo. No lleva campos, constantes, eventos, constructores ni nada static.
  • class Cuadrado : Figura, Poligono, Etiquetado: como en C#, la clase base y las interfaces van en la misma lista, la base primero. El primer nombre puede ser también una interfaz; lo decide el compilador. En BP: class Cuadrado extends Figura implements Poligono, Etiquetado.
  • @implement{ I } es obligatoria en lo que la clase declara para cumplir una interfaz: nombra una de las suyas que tenga ese miembro, también heredado (area es de Forma, y vale Poligono, que la hereda). Lo que pone el padre no se marca.
  • @override{} es opcional en lo que redefine un método o una property del padre: no cambia nada, lo deja escrito; si no redefine nada, es un error. Una declaración puede llevar varias anotaciones, como nombre().
  • Se usan como un tipo más: variables, parámetros, arrays, is, (Poligono) f y ==. Una interfaz no se construye. Un Thread y sus hijas no implementan interfaces (manual §9.8).

15. Hilos y parallel

Los hilos de BP son hilos de verdad, que el planificador de la VM alterna y que, en una placa de dos núcleos, corren a la vez (manual §14). En JC se escriben de tres maneras: 

module Hilos
{
   public class Calculo
   {
      public function void suma(int n)
      {
         int s = 0;
         for (int i = 1; i <= n; i++) s += i;
         println("suma hasta ", n, " = ", s);
      }
   }

   public class Contador : Thread
   {
      private string nombre;

      public function Contador(string nombre) : base(2048)
      {
         this.nombre = nombre;
      }

      public function void run()
      {
         println(this.nombre, " corre en su hilo");
      }
   }

   function int sumaRango(int a, int b)
   {
      int s = 0;
      for (int i = a; i <= b; i++) s += i;
      return s;
   }

   function void main()
   {
      parallel
      {
         case t1 = new Thread(2048):
            println("t1 = ", sumaRango(1, 100));
         case t2 = new Thread(2048):
            println("t2 = ", sumaRango(101, 200));
      }
      println("los dos han acabado");
      Contador c = new Contador("contador");
      c.start();
      c.join();
      Calculo k = new Calculo();
      Thread h = new Thread(k::suma(10));
      h.start();
      h.join();
   }
}

  • parallel { case t1 = new Thread(2048): … default: … } arranca un hilo por cada case, con la pila que dice (en bytes), y los espera todos en la }. El default, si lo hay, corre en el hilo que llama mientras tanto. Es el parallel … endpar de BP, con case t1 := Thread(2048).
  • Lo que ve un case: sus propias locales, las funciones, las clases y las constantes del módulo. Las variables del módulo y las locales de la función que lo contiene, no: para compartir datos, un objeto (manual §14.3).
  • Una clase hija de Thread pide su pila con : base(2048) y escribe su run(); start() la arranca y join() la espera.
  • new Thread(objeto::metodo(args)) lanza un método en otro hilo, sin escribir la clase: lo que se hace con una lambda en C#.
  • Lo compartido entre hilos se protege con un Mutex, una SyncList o una property sync. Cada println sale entero. En una placa de dos núcleos, t1 y t2 pueden salir en otro orden.

17.2 Si vienes de Java o de C#

Lo que compila igual que en Java o en C#, pero hace otra cosa, o se escribe un poco distinto:

  • Un miembro de clase sin marca es protegido, no privado como en C# (§10.2). Y un campo nunca es público: se expone con una property.
  • Las funciones y los métodos se declaran con function, y todo método es virtual salvo los private.
  • print no salta de línea; println, sí (§2.3).
  • == entre cadenas compara el texto, también en lo que viene de Java; y las cadenas no tienen métodos: len(s), upper(s)… (§6.5).
  • int a, b = 3; sólo da valor a b, como en C# (§6.2).
  • Un real sin letra es un double, como en C#; en las placas suele convenir el float, 1.5f (§6.3).
  • Un evento avisa más tarde: raise lo encola y sigue, y tiene un suscriptor (§13).
  • Un objeto con dueño se destruye en el momento, con su destructor; el recolector se ocupa del resto (§10.5).
  • El for es un contador, con el límite incluido y calculado una vez (§8.2).
  • Una List guarda Object: List<Sensor> para que el compilador sepa lo que guarda (§12).
  • Una excepción que nadie atrapa acaba su hilo; los demás siguen (§14).

17.3 Lo que choca con BP

Lo que hay que saber al traducir de un lenguaje al otro (§18.3):

  • Un nombre de BP que en JC es una palabra reservada —base, int, bool, new, is, static, void, foreach, protected, println…— no se traduce: el traductor lo dice, con su línea, y no renombra nada.
  • Al revés, un nombre de JC que en BP es una palabra reservada —step, next, end, then, loop, to, mod, and…, en mayúsculas o en minúsculas, porque las de BP no las distinguen—, tampoco: el traductor lo dice, con su línea («el nombre «step», que en BP es una palabra reservada»), y no renombra nada. Si piensas traducir, evítalos.
  • Lo de BP que JC no puede escribir: un for con el paso en una variable, un do … loop sin condición y un inline entre otras sentencias. El traductor lo dice.
  • Lo de JC que BP no puede escribir: (Caja) x cuando el constructor de Caja acepta x, porque en BP Caja(x) construiría. El traductor lo dice.
  • La forma escrita de un literal no viaja: 'a' llega a BP como 97, y 0xFF, como 255.
  • Los comentarios y las líneas en blanco no viajan: la traducción sale sin comentarios, con el formato del traductor.

18. Compilar, traducir y el IDE

18.1 Compilar un .jc

Como un .bp: el compilador elige el lector por la extensión, y lo demás es común. Las opciones son las de siempre (referencia §16.1): 

java -jar basicplus-frontend.jar Programa.jc --compile out --backend=mivm
  • El .mod es el mismo que daría el programa escrito en BP, y el .dbg apunta al .jc y a sus líneas: el depurador para en los .jc sin hacer nada más.
  • Las funciones native pasan por el AOT igual que las de BP.
  • Los import encuentran los .bp y los .mod; un .jc importado, compilado antes (§5.4).

18.2 Un proyecto

Un .bpbuild (referencia §16.2) con "main": "Programa" busca src/Programa.bp y, si no está, src/Programa.jc. Con los dos a la vez, no adivina: lo dice («el main está dos veces, Programa.bp y Programa.jc: el proyecto no sabe cuál compilar») y no compila. La lista sources admite .jc, y se compila en su orden, así que un módulo en JC que importa otro en JC va detrás de él: 

{
  "sourceDir": "src",
  "outDir":    "out",
  "main":      "Programa",
  "sources":   ["src/Utiles.jc", "src/Programa.jc"]
}
java -jar basicplus-frontend.jar --project app.bpbuild

Con los ficheros de §5.4 en src, compila Utiles, después Programa y, porque Programa lo importa, Viejo.bp.

18.3 Traducir entre BP y JC

El compilador traduce un fuente al otro lenguaje y lo escribe por la salida. Traduce el árbol ya analizado, así que sabe dónde va cada new, qué llamada es una conversión y qué tipo tiene una constante que en BP no lo escribe.

module Saludo

  • Los comentarios no viajan, ni las líneas en blanco: la traducción tiene el formato del traductor (tres espacios de sangría en JC; dos en BP).
  • Lo que no tiene forma en el otro lenguaje (§17.3) no se traduce: sale «no soportado», con el motivo y la línea del original, y el código de salida es 2. Si el original no compila, 3. Bien, 0.
  • Con una carpeta, --escribir-jc y --comprobar-jc recorren todos sus .bp y dan las cuentas: los que se traducen, los que no y por qué.
  • El programa traducido es el mismo: compilado, da el mismo .mod, salvo donde el print de BP usa la coma, que en JC es una pieza " " y escribe lo mismo con otro código.

18.4 En el IDE

Lo justo; el detalle, en la guía del IDE.

  • Los .jc se abren, se editan y se guardan como los .bp, y salen en el árbol del proyecto. El coloreado y el plegado, por llaves, van por la extensión del fichero; al guardar uno nuevo sin extensión, el IDE pone la del lenguaje del editor.
  • Compilar, ejecutar y depurar funcionan igual, en el PC y en la placa, con los puntos de parada en las líneas del .jc. En un proyecto, el main puede ser <main>.jc; con los dos, el IDE lo dice antes de tocar nada.
  • Edit → «Traducir a JC» y «Traducir a BP» guardan el fichero activo y abren su traducción en una pestaña nueva, sin guardar. Lo que no se traduce lo dice la consola, con su motivo.
  • Project → New Project crea el main en BP. Para tenerlo en JC: «Traducir a JC», guardar la pestaña como src/<main>.jc y borrar el .bp.

18.5 Los mensajes de error

  • Los errores de sintaxis son de JC: [línea:columna] error sintáctico: … (o error léxico). El lector de JC para en el primero.
  • Muchos dicen cómo se escribe en JC: «en JC es 'base', como en C#»; «en JC, ++ y -- van detrás: v++;»; «JC no tiene el ?? de C#, de momento (el ternario, c ? a : b, sí)»; «'Perro(…)' crea un objeto: en JC se escribe 'new Perro(…)'».
  • Los demás errores —tipos, nombres, visibilidad— los da el análisis, que es el de BP, y algunos hablan en BP: i += 1.5 da «'+=': 'integer' + 'double' da 'double', que no se guarda solo en 'integer' (como en C#: escribe la conversión, x := integer(x + …))», que en JC es i = (int) (i + 1.5);. Las tablas de este volumen dan la equivalencia.
