BasicPlus — Manual del lenguaje

Lenguaje estructurado tipado, orientado a módulos. Frontend en Java compila a un bytecode propio (formato .mod v9, "MOD9") ejecutado por la VM bpgenvm (mark-and-sweep GC, manejo determinístico de owners, excepciones tipadas).

1. Introducción

BasicPlus (BP) toma la sintaxis amable de Basic / Pascal y la combina con semántica moderna: clases con herencia simple, módulos como units Modula-2-style, manejo de excepciones, y "ownership" determinístico para liberación inmediata de recursos.

El pipeline general es:

// 1) Compilación: cada módulo → un .mod (binario, con su interfaz dentro)
java -jar basicplus-frontend.jar samples/hola.bp --compile out --backend=mivm

// 2) Ejecución: la VM carga el .mod raíz; los .mod de los imports los
//    busca por su nombre, <library>.<Module>.mod (§10.3)
java -jar bpgenvm.jar out/Hola.mod

2. Hola mundo

module Hola

  function main(arg: string)
    print "hola, " + arg
  end main

end Hola

Mínimo: un module, una function main(arg: string), y end emparejados. La VM pasa al main una cadena vacía si no hay argumentos; cómo pasar uno (y darle un valor por defecto), en §10.2.

print escribe sus piezas una detrás de otra: la coma pone un espacio entre dos, y el punto y coma, nada. Al final salta de línea, salvo si acaba en ;: entonces deja la línea abierta y el siguiente print sigue en ella (V8). Un print sin nada sólo salta. 

print "x =", x              // x = 7
print "["; x; "]"           // [7]
print "a";
print "b"                   // ab

La línea abierta sale entera con el siguiente salto (§14.5), así que un trozo no se ve hasta entonces; si el hilo acaba antes, sale tal cual.

3.2 Identificadores

Letra o _ seguido de letras, dígitos o _. Case-sensitive, y de 63 caracteres como máximo (uno más largo es error de compilación; la firma completa de una función —su nombre con los tipos de sus parámetros— admite 160). Los nombres que empiezan por doble guion bajo (__nombre) son del sistema: las primitivas de la VM y los nombres que sintetiza el compilador (__init, __prop_get_x…). Declarar uno —una variable, un campo, un parámetro, una clase, una constante, un enum, una property o una función privada— es un error de compilación (V7).

3.5 Continuación de línea

El salto de línea termina la sentencia, salvo dentro de paréntesis o corchetes abiertos: ahí el salto no es significativo y la expresión continúa en la línea siguiente. Para partir una expresión larga, enciérrala en ( ): 

print ("total = " + intToString(a)
    + " / " + intToString(b))      // OK: dentro de ( )

var v: integer[] := [1, 2,
                       3, 4]          // OK: dentro de [ ]

Los tipos estrechos (byte/int8/ word/int16) son tipos de almacenamiento: en arrays y campos ocupan 1-2 bytes por elemento; en la pila y en expresiones operan como integer (la lectura extiende con o sin signo según el tipo). Asignar un literal fuera de rango es error de compilación con el rango exacto en el mensaje.

Un string es siempre UTF-8 válido, y no cambia (V8). Lo que viene de fuera —un fichero, una línea, un paquete de la red, un byte[]— se descodifica al convertirlo en texto: fromBytes(b), readFile(ruta), TextFile.readLine() y readStr(n), Net.Tcp.recvStr(…). Si los bytes no son UTF-8 válido (un fichero en Latin-1, por ejemplo), lanzan EncodingError, hija de RuntimeError, con el sitio. Con un último argumento true (ignorarError), en vez de la excepción, cada trozo malo pasa a «�» (U+FFFD), como dice el estándar de Unicode: 

var t: string := readFile("latin1.txt", true)   // "año" en Latin-1 (61 F1 6F): a�o
try
  t := readFile("latin1.txt")
catch e: EncodingError
  print e.msg      // readFile('latin1.txt'): UTF-8 mal formado en el byte 1 (0xF1)
endtry

readLine() deja leída la línea mala: un bucle con try sigue con la siguiente. recvStr espera el resto de un carácter que llega partido entre dos paquetes. Y appendChar con algo que no es un carácter —un sustituto de UTF-16 (0xD800 a 0xDFFF) o un número fuera de 0..0x10FFFF— también lanza EncodingError, sin argumento para ignorarlo: es un fallo del programa. Para el texto que cambia, StringBuilder.

Una salvedad de double en el RP2350 (Pico 2, Metro): los valores subnormales —los que están por debajo de 2.2250738585072014e-308— se aplastan a 0. Todo lo que esté por encima de esa frontera es exacto, y byte-idéntico al PC, al ESP32-P4 y al STM32. El motivo es que el SDK de esa placa usa unas rutinas de coma flotante optimizadas que descartan los subnormales a cambio de velocidad (medido: recuperarlos costaría un 24 % de tiempo en toda la aritmética de double). En la práctica no afecta a nada: double se usa para medidas que piden precisión, y la instrumentación se mueve en 6 u 8 dígitos significativos, no en potencias de diez negativas de tres cifras. Lo único que conviene saber es que un cálculo que desborde por abajo dará 0 en esa placa y un número diminuto en las demás.

4.1.1 Promoción y casts

En operaciones mixtas y asignación hay promoción automática al tipo más ancho: integer → long → float → double (los estrechos suben primero a integer). La dirección contraria NUNCA es implícita: estrechar requiere un cast explícito con la sintaxis de llamada del tipo destino: 

var d: double := 3.9d
var i: integer := integer(d)     // 3 — trunca hacia cero (integer(-3.9d) = -3)
var L: long    := long(i)        // widening explícito también disponible
var f: float   := float(L)
var b: byte    := byte(i)        // valida el RANGO en runtime:
                                  // fuera de 0..255 lanza RuntimeError (atrapable)

Los casts numéricos son integer(x), long(x), float(x), double(x) y los estrechos byte(x), int8(x), word(x), int16(x). integer(x) sobre un float/double trunca hacia cero; para redondear usa floor, ceil o round. El cast de un literal fuera del rango del tipo destino se rechaza en compilación.

4.2 Arrays

Un array es una secuencia indexable de elementos del mismo tipo. BP distingue dos variantes según se conozca o no el tamaño en tiempo de declaración, y eso determina dónde se aloja el almacenamiento.

4.2.1 Arrays de tamaño fijo  T[N]

Un array fijo no es una referencia: es almacenamiento en sitio. Vive en el marco de la función (variable local) o dentro del objeto (campo private var de una clase), y sólo se puede indexar (buf[i], con comprobación de rango en ejecución), recorrer (for x in buf) y medir (len(buf)). Cualquier otro uso —asignarlo a otra variable, pasarlo a una función, devolverlo, guardarlo en un campo— es error de compilación: no hay referencia que dar, y por eso no puede escapar ni sobrevivir a su dueño. El tamaño es un literal entero > 0 y los elementos son primitivos (enteros, estrechos, long, float, double, boolean; para string o clases usa T[]). Un inicializador literal puede ser más corto que N: el resto queda a cero.

ÁmbitoDónde vive
Local de funciónEn el marco: 4 + ⌈N·ancho/4⌉·4 bytes (los datos se redondean a 4: un byte[3] ocupa 8), a cero al declararlo. Ni heap ni GC.
Campo private var de claseDentro del objeto: 1 + ⌈N·ancho/4⌉ ranuras (hasta 255), a cero al construirlo. Sólo lo indexa la propia clase.
Global de móduloNo (error de compilación): a nivel de módulo escribe T[], con un literal […] o newIntArray(N)/newByteArray(N)/newLongArray(N).
public class Media
  private var muestras: integer[8]      // en el objeto
  var n: integer := 0                   // cuántas lleva
  public function add(v: integer)
    this.muestras[this.n mod len(this.muestras)] := v
    this.n := this.n + 1
  end add
end Media

function Main()
  var buf: byte[64]                    // en el marco, a cero
  var mascara: byte[4] := [1, 2, 250]   // el 4.º queda a 0
  buf[0] := 42
  print len(buf)                       // 64
  // suma(buf)   ← error: no es una referencia (cópialo a un T[] si hay que pasarlo)
end Main

4.2.2 Arrays de tamaño variable  T[]

El tamaño se decide en tiempo de ejecución. El array se aloja en el heap (opcode NEWARRAY) y se referencia mediante una ref — un handle de 64 bits con contador de generación, no una dirección: usar un objeto ya liberado falla en el acto en vez de corromper en silencio. Gestionado por el GC. 

// Desde un literal: el frontend emite NEWARRAY n + ASTORE de cada elemento
var primos: integer[] := [2, 3, 5, 7, 11]

// Desde una función: split, listDir, etc. devuelven arrays
var partes: string[] := split("a,b,c", ",")
var ficheros: string[] := listDir(".")   // ordenados; en las dos VMs y en la placa

La VM usa cinco tipos físicos en el heap según el ancho del elemento: TYPE_ARRAY_I8 (byte/int8 y strings UTF-8), TYPE_ARRAY_I16 (word/int16), TYPE_ARRAY_I32 (integer; también floats, 4 bytes opacos), TYPE_ARRAY_I64 (long/double, 8 bytes por elemento) y TYPE_ARRAY_REF (8 bytes por elemento: handles a objetos, escaneado por el GC). El array lleva su propia longitud como primer slot. En los anchos estrechos, la lectura extiende el valor a i32 (con o sin signo según el tipo) y la escritura trunca al ancho del elemento.

4.2.3 Acceso e iteración

Indexado con arr[i] (0-based). for-in recorre todos los elementos (ver §7.3). 

for n in primos do
  total += n
next n
Para colecciones dinámicas (crecen, encogen, mezcla de tipos), usa List o OwnerList en lugar de T[]. Los arrays T[] tienen tamaño fijo tras su creación (no hay append); List redimensiona internamente.

4.3 Enums

public enum Dia
  LUNES               // = 0
  MARTES              // = 1
  MIERCOLES
  JUEVES
  VIERNES
  SABADO := 10          // salto explícito
  DOMINGO             // = 11
end Dia

var d: Dia := Dia.MIERCOLES

Los enums son nombres simbólicos para constantes integer. Auto-numeran desde 0 salvo asignación explícita.

Un enum es un tipo propio y cerrado: un entero no se convierte en él —Dia(2) es error de compilación: «'Dia' es un enum: no se llama ni se convierte desde un entero (usa Dia.VALOR)»—. Al imprimirlo, o en una cadena, sale su número: con d de arriba, print "d=" + d da d=2, como print d (V7).

4.4 Clases

Cualquier class Foo ... end Foo introduce un tipo Foo usable como tipo de variable, parámetro y retorno. Las refs admiten null.

4.5 any

Tipo interno, bidireccionalmente asignable: cualquier ref entra, y cualquier tipo destino acepta un valor any. No se puede escribir any como tipo en BP source.

Ojo si vienes de una versión anterior: las colecciones YA NO usan any. Desde V5, List.add toma Object y List.get devuelve Object — y Object no es bidireccionalmente asignable: sacar una entidad pide un downcast explícito. 

var p: Persona := l.get(1)             // V4: valía. Hoy NO compila.
var p: Persona := Persona(l.get(1))    // V5: el cast, explícito.

El cambio es deliberado: any dejaba pasar cualquier cosa y el fallo aparecía tarde. Con Object el compilador te obliga a decir qué esperas, y si no lo es, falla ahí mismo. Para valores sueltos hay atajo sin cast — los captadores tipados de List, en la referencia.

El cast Clase(x) baja desde un Object o desde cualquier antepasado de la clase (Perro(a) con a: Animal); si el valor no es de esa clase, lanza en ejecución. Si la clase tiene un constructor que acepta ese argumento, gana el constructor.

5. Declaraciones

5.1 var

var nombre: string
var edad:   integer := 30
var total:  long := 0L
var media:  double
var x, y, z: integer                  // múltiples nombres
var pts: integer[100]                  // array fijo (§4.2.1)
var p: Punto := Punto(3, 4)             // ref a clase

Una variable global siempre vale lo que dice su declaración. Las globales —las var y las property de módulo, y las var y las property estáticas de una clase— viven en el espacio de constantes del módulo: sin valor inicial valen 0 (o null; un string, ""); con un valor literal (numérico/boolean/string), queda grabado en el .mod, sin código de arranque, y la variable sigue siendo reasignable. Cualquier otro valor inicial —un array literal, una llamada, un objeto, una expresión— se calcula al cargar el módulo, en el orden en que están escritas, después de inicializarse los módulos que importa y antes de su función inicializadora (la función con el mismo nombre que el módulo), que ya las encuentra puestas.

Un string global o un campo string sin valor —que nadie ha asignado— vale "": se imprime y se concatena como "", len da 0 y charAt(s, 0) lanza el mismo RuntimeError que con "" («charAt: idx fuera de rango 0 (len=0)»), igual en las dos VMs. (Un string es un escalar: no admite null; asignárselo es error de compilación.) Un array global o un campo array sin valor sí es null: len da 0 y un for sobre él no da ninguna vuelta, pero indexarlo lanza un RuntimeError (índice fuera de rango), igual en las dos VMs; y print no enseña su contenido (de uno sin valor imprime 0).

Una variable local se inicializa antes de leerla. Una var de módulo sin inicializador vale 0 (o null; un string, ""): vive en el bloque de datos del .mod. Una local sin inicializador tiene un valor indeterminado —lo que hubiera en la pila—, así que leerla antes de darle valor es un error de compilación, con su línea. El compilador comprueba que, por todos los caminos que llegan a una lectura —las ramas de un if, los case de un switch, un while que puede no ejecutarse, un catch…—, la variable ya tiene valor. Declararla sin valor y asignarla después está bien (#540, V7). 

var total: integer          // sin valor todavía
if n > 0 then
  total := n
else
  total := 0
endif
print total                 // bien: tiene valor por los dos caminos

5.2 const

public const PI: float := 3.14159
public const MAX_MS: long := 86400000L
const SALUDO: string := "hola"
const DEBUG: boolean := false
const MIN: integer := -40             // '-' sobre literal, OK

Una const de módulo exige un literal primitivo (integer/float/long/double/boolean/string, con - opcional) — el valor se inlinea en cada uso, no ocupa slot, y las públicas viajan en la interfaz para que los importadores también las inlineen. Para un valor calculado o de tipo no-primitivo usa una var asignada en la función inicializadora del módulo. No es asignable en ningún ámbito y no existen const arrays (§4.2.1).

5.3 var owner

var owner r: Recurso := Recurso("db")
// al salir de la función —fin normal, return o excepción— el objeto se
// DESTRUYE (§9.4b): primero lo que posee, cada uno con su destructor, y
// después él (~Recurso). Varios owners mueren en orden INVERSO al de declaración.

Un var owner local no puede escapar: ni devolverse con return ni guardarse en un campo o en un array (error de compilación), porque al salir de la función el objeto ya no existe. Pasarlo como argumento sí vale (un préstamo). Y para soltar un recurso al salir de un bloque, no de la función: 

try var f: IO.TextFile := IO.TextFile("datos.txt", "r")
  while not f.eof() do
    print f.readLine()
  endwh
endtry                // f se destruye aquí (~File() cierra el fichero), salgas por donde salgas

try var es azúcar: el recurso es un var owner del ámbito de fuera y el finally lo suelta; admite catch y finally como cualquier try (el recurso se suelta después de ellos). Detalle en §12 Owner semantics.

7. Control de flujo

7.1 if / elseif / else

if edad < 18 then
  print "menor"
elseif edad < 65 then
  print "adulto"
else
  print "senior"
endif

7.2 while / do

while i < n do
  total := total + i
  i := i + 1
endwh

do
  i := i + 1
loop i < 100           // do-while: el cuerpo corre al menos una vez; sigue mientras la condición sea cierta

do
  i := i + 1
  if i > 105 then break
loop                    // sin condición: bucle infinito, se sale con break

El bucle con la condición al final se cierra con loop [condición] (no hay do … while).

7.3 for

Dos variantes: numérico y foreach (for-in).

// Numérico: i := from to to [step]
for i := 0 to 9 do
  print i
next i

for i := 1 to 10 step 3 do
  print i                // 1 4 7 10
next i

// Foreach sobre un array (fijo o variable, cualquier tipo de elemento)
var primos: integer[] := [2, 3, 5, 7, 11]
for n in primos do
  total += n
next n

El cuerpo se cierra con next [nombre] (no endfor); el nombre tras next es opcional y, si está, debe coincidir con la variable de iteración (uso documental).

step es un integer con signo: una constante (step -1 cuenta hacia abajo) o una expresión, que se evalúa una sola vez antes de entrar; si el paso es negativo el bucle sigue mientras i >= hasta. step 0 escrito es error de compilación.

7.4 switch

switch dia
  case Dia.SABADO, Dia.DOMINGO
    print "fin de semana"
  case Dia.LUNES
    print "a trabajar"
  default
    print "laborable"
endsw

El sujeto es un entero (integer, long, byte…), un boolean, un enum o un string, que se compara por su contenido. Un case puede listar varios valores, y cada uno es su propio bloque: no hay caída al siguiente. Un real (float/double) o un objeto como sujeto es un error de compilación —la igualdad exacta de reales es una trampa, y comparar referencias es cosa de if— (#546, V7). 

switch orden
  case "ls", "dir"
    lista()
  case "cd"
    cambia()
  default
    print "no conozco " + orden
endsw

7.5 break / continue

break sale del while, do, for o switch más cercano; continue salta a la próxima iteración del bucle más cercano (un switch no es un bucle: un continue dentro de un case sigue con el bucle que lo contiene).

7.6 parallel / endpar

Azúcar sintáctico para arrancar varios threads sin escribir una subclase de Thread por cada uno. Cada case introduce un thread cuyo cuerpo es el del bloque; el default (opcional) corre en el thread llamador entre los start()s y los join()s; tras endpar todos los threads están joineados. 

function main(arg: string)
  parallel
    case t1 := Thread(2048)
      var r: integer := sumaRango(1, 10000)
      print "t1 = " + intToString(r)

    case t2 := Thread(2048)
      var r: integer := sumaRango(10001, 20000)
      print "t2 = " + intToString(r)

    default
      // corre en el thread llamador; ve sus locales y globals
      print "default mientras t1/t2 trabajan"
  endpar
  print "todos joineados"
end main

Equivalente conceptual al patrón largo (class W extends Thread …; W().start(); W().join()), pero el compilador sintetiza una subclase anónima de Thread por cada case, con el cuerpo del case como su run(). Las variables t1, t2, … son visibles en el scope encerrador tras endpar: ya están joineadas y son inspeccionables.

El primer token tras := debe ser literalmente Thread con un argumento entero (el stack del worker). Para state propio del thread con campos, usa el patrón clásico de subclase de Thread.

Reglas de visibilidad del cuerpo del case (encapsulación de objeto — ver 14.3):

SímboloVisible
Locales declaradas en el propio cuerpo✓
stdlib (print, intToString, yield(), Mutex, ...)✓
Clases, funciones, consts del módulo✓
Variables globales (var) del módulo✗ error semántico
Locales del encerrador✗ "identificador no resuelto"

El bloque default, en cambio, corre en el encerrador y ve TODO: locales, globals, etc. Para que las ramas se coordinen comparten estado vía objetos (Mutex, List, clases compartidas).

8. Funciones

public function suma(a: integer, b: integer): integer
  return a + b
end suma

function imprimir(msg: string)        // sin ': T' → void
  print msg
end imprimir
  • public → exportada en la interfaz, llamable cross-library.
  • Por defecto, las funciones son privadas al módulo.
  • El tipo de retorno se declara con : T tras los paréntesis. Si se omite, la función es void.
  • Sólo retorno con return [valor]. Sin retorno explícito, void.

8.1 Parámetros con valor por defecto

public function label(text: string, prefix: string := "[", suffix: string := "]"): string
  return prefix + text + suffix
end label

label("hola")              // "[hola]"
label("hola", "<")         // "<hola]"
label("hola", "<", ">")    // "<hola>"

Un parámetro con := valor es opcional en la llamada. Reglas:

  • El valor por defecto debe ser un literal constante (numérico, string, boolean).
  • Los parámetros con default van al final de la lista; los argumentos se rellenan por posición.
  • El default se sustituye en el llamante en compilación (cero coste en la VM) y viaja en la interfaz: funciona igual al llamar funciones de otra librería.

8.2 Tuplas (retorno múltiple)

// Una función puede devolver VARIOS valores: tipo tupla (T1, T2, ...)
function divmod(a: integer, b: integer): (integer, integer)
  return (a / b, a mod b)
end divmod

// Desempaquetado con { ... } := sobre lvalues ya declarados
var q: integer := 0
var r: integer := 0
{ q, r } := divmod(17, 5)        // q=3, r=2

Las tuplas son first-class: además de desempaquetarse al vuelo, se pueden guardar en una variable, pasar como parámetro y devolver almacenadas. Los destinos del desempaquetado pueden ser lvalues cualesquiera, no solo variables: 

var t: (integer, string) := pair()   // guardar la tupla
{ n, s } := t                          // ... y desempaquetar después

{ arr[0], arr[1] } := coords()        // a elementos de array
{ p.x, p.y } := coords()               // a campos de objeto

Una tupla no se imprime directamente (print t es error): desempaquétala primero. Los receptores del { ... } := deben existir ya (no declara variables). Y una tupla no entra en una colección: List.add toma Object y una tupla no lo es (§4.5); guárdala en una clase pequeña si la necesitas en una lista.

8.3 Funciones native (AOT)

Una función marcada native function es candidata a compilación AOT (Ahead-Of-Time): además del bytecode normal, el compilador puede traducirla a C nativo del micro, que se ejecuta directamente (sin el bucle del intérprete) para acelerar kernels de cómputo calientes. 

native function sumaCuadrados(n: integer): integer
  var s: integer := 0
  var i: integer := 1
  while i <= n do
    s := s + i * i
    i := i + 1
  endwh
  return s
end sumaCuadrados
  • Aditivo: el .mod SIEMPRE contiene el bytecode de la función. El código nativo viaja dentro del mismo .mod (su sección native; ya no hay un .mdn suelto de la aplicación) y el runtime lo usa si es de la arquitectura del micro y de la versión de su firmware (su ABI); si no, la función corre interpretada —el de otra versión, como el de un .mod de V6, se rechaza con un aviso—. No compilar el AOT nunca rompe el programa.
  • Comportamiento por plataforma:
    PlataformaFunción native
    Raspberry Pi Pico 2 / Metro (RP2350, ARM Cortex-M33) Acelerada por AOT (≈40–90× en kernels enteros).
    STM32 (Nucleo-U575, Discovery U5G9J; ARM Cortex-M33) Acelerada por AOT — mismo código Thumb-2 que el RP2350 (≈45× medido en un kernel LZSS en placa).
    ESP32-P4 (RISC-V con FPU) Acelerada por AOT (destino riscv —riscv32-esp-p4—, desde V4).
    ESP32-C5 / ESP32-C3 / ESP32-C6 (RISC-V sin FPU) Acelerada por AOT (destino riscv-imc, ABI ilp32, desde V7; probada en placa en la C5, la C3 y la C6). Sin FPU, cada operación de float la hace el firmware —la misma rutina que usa el intérprete—: da exactamente lo mismo, pero acelera menos que el código entero.
    ESP32-S3 (Xtensa LX7) Interpretada — misma semántica, sin speedup. El AOT emite ARM y RISC-V, no Xtensa; sin fecha, fuera del plan.
    VM de PC (host) Interpretada (hay un camino AOT host sólo para pruebas).
  • Subset soportado: funciones y métodos sobre primitivos (integer, long, float, double, boolean, estrechos), string, arrays de cualquier tipo de elemento (crearlos con newIntArray/newByteArray/newLongArray/newDoubleArray e indexarlos), objetos, variables de módulo, las conversiones estrechas (byte(x), int16(x)…, con el rango y el mensaje del intérprete) y cualquier función intrínseca de la stdlib —Math.sin, sqrt, startsWith, sleep…, las que tienen el cuerpo inline CALL_BUILTIN (§8.3b)—: la native llama al MISMO código del builtin que el intérprete, así que da lo mismo. Un fallo en runtime (índice fuera de rango, referencia null) o un throw RuntimeError("…") dentro de la native se propaga al try/catch que lo envuelva —desde V7, también uno DENTRO de la propia native, con su catch por clase y su finally—, con el mensaje del intérprete (la línea exacta dentro de la native, todavía no). Lo que aún NO cabe — try var (el recurso que el bloque suelta) dentro de la native, tuplas con campos float, long o double (las demás sí, desde V7), instanceof, eventos, parallel, for … in, leer o escribir campos (propios o heredados: usa un getter), llamar a métodos o properties estáticos, super y Heap.compact() — lo rechaza el compilador con su mensaje y la línea. Los arrays fijos locales tipo[N] tampoco (error de compilación): usa newIntArray/newByteArray/newLongArray. Igual en un método native de clase: es el mismo error, con el método y la línea (#519, V7). El detalle vivo está en docs/AOT_LIMITES.md.
  • Una native se porta como un hilo más (V7): si llama a algo que bloquea —sleep, el lock() de un Mutex ocupado, una función BP que espera— se suspende y los demás hilos siguen; en un cálculo largo cede el turno cada 5 ms —lo mira en sus bucles: en cada vuelta de un bucle que llama a algo, por una marca que el reloj de la placa sube cada 5 ms, así que cede a tiempo aunque cada vuelta sea lenta; y cada 1024 vueltas en uno sin llamadas, cuyas vueltas son cortas por fuerza—, y el Stop del IDE la para aunque esté en un bucle infinito. Una recursión cuenta como un bucle: una native que se llama a sí misma —o a otra que la vuelve a llamar— lo mira al entrar, cada 1024 llamadas, así que también cede y se para aunque no tenga bucles. Por dentro corre en un hilo propio de la plataforma y se pasa el testigo con el intérprete; una native que no puede ceder (sin bucles, sin recursión y sin llamadas que bloqueen) corre directa, sin ese paso.
  • Velocidad y double: ninguna de las placas tiene FPU de doble precisión, así que un double en una native lo emula el firmware y acelera mucho menos que el código entero. Medido en una ESP32-C3 (sin FPU) con el mismo bucle nativo e interpretado: con enteros, unas 100 veces más rápido; con double, 5 veces (307 ms frente a 1609); con float, que allí también se emula, casi 6 (200 frente a 1141). El suelo lo pone la emulación, no el intérprete. Si buscas velocidad en el micro, usa float: las placas con FPU de simple precisión (Cortex-M33, ESP32-P4) lo hacen con una instrucción.
  • Depurar: en el PC una native corre interpretada y se depura como cualquier función; en la placa, el depurador no para dentro de ella (corre como código máquina), y el IDE lo dice al poner un breakpoint dentro. Para seguirla paso a paso en la placa, quítale native: sirve para verificar el algoritmo; pónselo cuando funcione. Lo que se depura es el algoritmo; que la traducción a C dé lo mismo que el intérprete es trabajo del compilador, y lo vigilan sus pruebas (cada native contra su versión interpretada, y cada placa contra el PC).
  • Llamar funciones BP normales desde una native es posible (el puente existe), pero cruza de vuelta al intérprete: lo ganado en velocidad se pierde en cada cruce. El compilador lo detecta y emite un warning de rendimiento. Si esa función se bloquea, la native se suspende con ella.
  • Cómo se genera el código nativo: el IDE lo hace automáticamente en Run on Device según la placa conectada: para RP2350/STM32 detecta el toolchain ARM bare-metal (arm-none-eabi-gcc — instalación estándar del Arm GNU Toolchain o PATH; se fija a mano en Project → AOT (toolchain)…; instalación: Guía del IDE §5.1); para las ESP32 RISC-V (la P4, la C3, la C5 y la C6), el riscv32-esp-elf-gcc de la instalación de ESP-IDF. Emite C, compila código PIC y lo funde en el .mod (en su sección native) antes de subirlo. Si no hay toolchain, avisa y el programa corre interpretado. El paso también puede hacerse a mano (AotMain emite C → gcc del destino → MdnPack empaqueta; el script bpgenvm-c/pico/build_mdn.sh encadena los tres para ARM).

8.3b Funciones intrínsecas: el cuerpo inline

Una intrínseca es una función normal cuyo cuerpo es bytecode escrito, una instrucción por línea, como el inline($CD/$21) de Turbo Pascal: 

public function sin(x: float): float
  inline CALL_BUILTIN 24
end sin

El compilador no genera código para ella en el .mod: en cada llamada mete ese bytecode tal cual, con los argumentos ya en la pila (el mnemónico es el de docs/OPCODES.md; el número, el id del builtin en las dos VMs). Así están escritas las funciones de Math, y su firma viaja en la interfaz del módulo como la de cualquier otra. Es la sintaxis de la biblioteca estándar y del módulo raíz; en un programa normal no hace falta.

8.4 Sobrecarga de funciones

Puedes declarar varias funciones con el mismo nombre siempre que se distingan por sus parámetros. El compilador elige la que encaja con cada llamada.

public function texto(n: integer): string
  return "int:" + intToString(n)
end texto

public function texto(s: string): string          // distinto TIPO
  return "str:" + s
end texto

public function texto(n: integer, veces: integer): string   // distinto NUMERO
  ...
end texto

Funciona con funciones libres, métodos estáticos, métodos de instancia y constructores. Y también entre módulos: al importar Fmt, las tres Fmt.texto(...) de arriba están disponibles y se resuelven igual — y desde V7 también las sobrecargas de los constructores (Lib.Punto(1, 2) y Lib.Punto(), y super(...) elige por firma) y las de los métodos estáticos (§9.6).

Lo que distingue una sobrecarga de otra

Sólo la lista de parámetros (número y tipos). El tipo de retorno NO cuenta: dos funciones que sólo se diferencien en lo que devuelven son la misma para el compilador.

function g(a: integer): integer ...
function g(a: integer): string  ...   // ERROR
error semántico: sobrecarga duplicada: 'g' con la misma firma de parámetros ya declarada

El motivo es que en el punto de llamada no siempre hay un tipo esperado con el que decidir: print g(1) no dice cuál de las dos quieres.

Sobrecarga y herencia: redefinir una NO tapa las demás

Si una subclase redefine una de las sobrecargas heredadas, las otras siguen ahí:

class Base
  public function saluda(): string ... // "base"
  public function saluda(n: integer): string ... // "base N"
end Base

class Hija extends Base
  public function saluda(): string ... // "hija" — sólo redefine ESTA
end Hija

var h: Hija := Hija()
print h.saluda() + " / " + h.saluda(7)   // -> hija / base 7

Es decir: la redefinición sustituye la versión con esa misma firma, y la de (integer) se hereda intacta.

Cuidado al mezclarla con valores por defecto

Una sobrecarga y un parámetro con valor por defecto pueden acabar aceptando la misma llamada. El compilador no adivina: lo rechaza.

function h(a: integer): integer ...
function h(a: integer, b: integer := 0): integer ...

h(1)    // las dos encajan
error semántico: llamada ambigua a 'h' con (integer): varias sobrecargas encajan por igual (usa un cast)

La salida limpia suele ser quedarse con una de las dos formas: o sobrecargas, o un valor por defecto, pero no las dos cubriendo el mismo caso.

9. Clases

public class Persona
  var nombre: string   // un campo NUNCA es público
  var edad:   integer

  public function Persona(nombre: string, edad: integer)
    this.nombre := nombre
    this.edad   := edad
  end Persona

  public function saludar(): string
    return "Hola, soy " + this.nombre
  end saludar
end Persona

9.1 Campos

var dentro de la clase declara un campo de instancia, y un campo nunca es público: se lee y se escribe por this.campo dentro de la clase (y de sus descendientes, abajo), y desde fuera no se toca. Marcar un campo public es un error de compilación, y el mensaje te manda a la alternativa correcta: public property (§9.5), que expone un get/set y deja el campo de respaldo privado. La razón es de diseño: lo que cruza la frontera del módulo es un contrato, no la representación interna.

Un campo admite un array de tamaño fijo tipo[N] si es private var: vive dentro del objeto y sólo lo indexa la propia clase (§4.2.1). Si tiene que verse o pasarse, declara tipo[] e inicialízalo en el constructor con newIntArray(N)/newByteArray(N)/newLongArray(N). Un campo es protegido (o private): lo ven su clase y sus descendientes, también los de otro módulo — desde V7 la interfaz publica los campos no privados con su ranura (§9.2.1); para exponer un dato a cualquiera, una property.

Inicializadores. Un campo (o una property) de instancia puede llevar := valor: var n: integer := 5, var s: string := "hola", public property etiqueta: string := "sin nombre". Se ejecutan una vez por objeto, en orden de declaración, dentro del constructor justo después del super(...) (escrito o implícito) y antes de su cuerpo — como en Java. Una clase con inicializadores y sin constructor recibe uno que los ejecuta: sin argumentos o, si su padre tiene constructor, uno por cada sobrecarga del padre, con sus mismos parámetros, que se los pasa con super(...) —así se sigue construyendo igual: Tarea(4096) con Tarea extends Thread—. El valor es una expresión cualquiera (un literal, una construcción, una llamada), pero no puede usar this ni otros campos: para eso está el constructor.

El tope de una clase. Una clase admite hasta 256 métodos (con los heredados y los accesores de sus properties) y 256 ranuras de campo (una referencia, un long o un double ocupan dos). Pasarse es un error de compilación con la línea de la clase.

9.2 Métodos

Como funciones pero dentro de la clase. El parámetro implícito this apunta a la instancia. Los métodos no-estáticos son virtuales (dispatch dinámico vía vtable) salvo los private, que se llaman directamente — ver 9.2.1.

9.2.1 Visibilidad: los tres niveles

Un miembro de clase tiene uno de tres niveles. El del medio es el que sale sin escribir nada, porque al montar una jerarquía lo normal es que la hija pueda usar lo de la madre:

Se escribeQuién lo ve¿Virtual?
publicTodo el mundoSí
(nada) — protegido Su clase y sus descendientes, aunque estén en otro módulo (métodos y properties y, desde V7, también los campos)Sí
privateSólo su propia claseNo
public class Base
  public function Base()
  end Base

  public function saluda(): string      // lo ve cualquiera
    return this.adorna(this.crudo())
  end saluda

  function adorna(s: string): string    // PROTEGIDO: la hija puede usarlo
    return "<< " + s + " >>"
  end adorna

  private function crudo(): string      // sólo esta clase, ni la hija
    return "hola"
  end crudo
end Base

No hay palabra virtual, y no hace falta: virtual es todo menos private. Un método protegido entra en la tabla de métodos igual que uno público — la diferencia entre ellos es quién puede nombrarlo, no cómo se llama ni cuánto cuesta.

private sólo tiene sentido dentro de una clase: a nivel de módulo, lo que no es public ya es privado del módulo, y ahí no hay descendientes a quien proteger. Y public private no existe: son excluyentes.

Al elegir: pon private cuando quieras poder cambiar o borrar ese método sin mirar quién hereda de la clase. Si lo dejas sin marcar, una hija —tuya o de quien use tu librería— puede estar apoyándose en él.

Entre módulos (desde V7): una hija declarada en otro módulo ve exactamente lo mismo que una del mismo módulo — métodos, properties y campos protegidos de su base (this.nombre vale), con final y private respetados. El único sitio donde un campo heredado sigue sin leerse es dentro de una función native (§8.3): ahí, un getter.

9.3 Constructor

Función con el mismo nombre que la clase. Se ejecuta al hacer NombreClase(args). La primera línea del constructor dice cómo se construye el objeto, y hay tres formas:

  • Nada — super() implícito (modelo Java): si la clase tiene base, el compilador inyecta la llamada al constructor sin argumentos del padre. Si el constructor del padre exige argumentos, la llamada explícita es obligatoria (error de compilación si falta). Si el padre no tiene constructor, no hay nada que llamar.
  • super(args) — el padre por ese constructor; debe ser la primera sentencia.
  • NombreClase(args) — delegación: este mismo objeto se inicializa por esa otra sobrecarga del constructor (que a su vez hace su super y los inicializadores), y después sigue el cuerpo. Sólo como primera sentencia: en cualquier otro sitio NombreClase(args) es un objeto nuevo, como siempre. Un constructor no puede delegar en sí mismo ni en ciclo, ni delegar y además llamar a super(...).

Los inicializadores de campos y properties corren después del super y antes del cuerpo, en el constructor que hace el super; el que delega no los repite.

Visibilidad. La de cualquier miembro: private es privado (sólo la propia clase lo construye o delega en él), public es público, y sin decir nada es protegido: lo usan la clase y sus subclases (desde super(...) o construyéndola), también las de otro módulo, pero no cualquiera. Un constructor no público de una clase pública viaja en la interfaz con su marca, y es el módulo que lo usa quien recibe el error.

9.4 Herencia

public class Animal
  var nombre: string
  public function Animal(nombre: string)
    this.nombre := nombre
  end Animal
  public function hablar()
    print "..."
  end hablar
end Animal

public class Perro extends Animal
  public function Perro(nombre: string)
    super(nombre)
  end Perro
  public function hablar()
    print this.nombre + " dice guau"
  end hablar
end Perro

Herencia simple. super.metodo(args) invoca explícitamente al método del padre dentro de un override. La herencia funciona también cross-module: la clase base puede venir de otra librería importada (vtable, campos protegidos, estáticos y super(...) por firma incluidos: §9.2.1 y §9.6). x instanceof Foo comprueba el tipo dinámico en runtime, y Foo puede ser cualquier clase, también una de otro módulo (o instanceof Lib.Base, e instanceof RuntimeError; desde V7).

La raíz. Una clase sin extends desciende de Object (toString(), compareTo(other)), que es una clase escrita en BasicPlus en Core.bp como Thread, Mutex y StringBuilder (§10.0). Object y Thread se declaran allí public root class: una root class no desciende de nada — por eso un Thread no es un Object: su run() tiene que ser el primer método de su tabla, que es lo que la VM arranca. root sólo puede escribirse en Core; en cualquier otro módulo es error.

9.4b El destructor: ~Clase()

public class Valvula
  var pin: integer := -1               // -1: todavía no tiene pin
  public function Valvula(pin: integer)
    Gpio.init(pin, Gpio.OUTPUT())
    Gpio.write(pin, 1)                 // abre
    this.pin := pin                    // ya es suyo: lo apunta al final
  end Valvula
  public function ~Valvula()           // el contrario del constructor
    if this.pin >= 0 then
      Gpio.write(this.pin, 0)        // cierra
      Gpio.release(this.pin)          // y el pin vuelve a como estaba
    endif
  end ~Valvula
end Valvula

«Qué significa destruir esto» se escribe una vez, en la clase, y no en cada sitio donde se usa. El destructor se llama como su clase, no lleva parámetros ni devuelve nada, y lo llama el lenguaje, nunca el código, cada vez que el objeto se libera, lo libere quien lo libere (V7, #668): al morir su dueño —un var owner local al salir de su ámbito, al reasignarlo o al acabar un try var (§5.3); un campo owner al reasignarlo o al destruirse el objeto que lo tiene—; cuando el GC lo recoge porque ya nadie lo alcanza (corre poco después, entre dos turnos del planificador); y al acabar el programa —también tras un error o un STOP—, todo lo que queda vivo con destructor, el más nuevo primero (con un tope de 3 s), para que todo vuelva a como estaba. Es virtual: corre el de la clase real del objeto, y al acabar el de una hija corre el de su padre. Toda clase tiene uno (Object lo declara vacío en Core.bp): sólo se sobrescribe cuando hay un recurso externo que soltar — un descriptor, una consulta, un mutex, un pin.

El orden: primero lo que el objeto posee —sus campos owner, y los de éstos, del último al primero— y después él; así que en su destructor, sus campos owner ya son null. Un destructor es código normal: puede esperar, tocar la GUI o hacer join de un hilo. Y si lanza una excepción, se dice (por el diagnóstico, con la clase) y la limpieza sigue con los demás: un destructor que falla no deja nada sin destruir.

Un recurso de la biblioteca, en un campo owner: las clases de dispositivos (Pwm.Slice, Gpio.Pin, Uart.Port…) ya sueltan lo suyo en su destructor (V7, #667, Referencia §14.1), así que una clase que las usa no necesita destructor: el suyo muere con ella, antes que ella. 

public class Motor
  var owner pwm: Pwm.Slice
  public function Motor(pin: integer)
    this.pwm := Pwm.Slice(pin, 20000)   // al morir el Motor, ~Slice para el PWM
  end Motor
end Motor

Un objeto cuyo constructor lanzó también se destruye: ya existe en memoria, y lo recoge el GC (o el final del programa). Una clase que toma el recurso ella misma, con las funciones de un módulo, ha de soltar en su destructor sólo lo suyo: lo apunta al final del constructor, cuando ya lo tiene, y lo suelta una vez —es lo que hacen las clases de la biblioteca, y lo que hace Valvula con su pin: si Gpio.init lanza, se queda en -1 y su destructor no toca nada—.

9.5 Properties

public class Punto
  var _x: integer
  public property x: integer
    get
      return this._x
    endget
    set(v)
      if v < 0 then
        throw RuntimeError("negativo")
      endif
      this._x := v
    endset
  endprop
end Punto

// Forma corta: backing field + getter/setter triviales auto-generados
public property y: integer

Una property sintetiza un campo respaldo y dos métodos getX/setX. Desde código se accede como un campo (p.x, p.x := 5).

Dentro de su get/set, field es ese campo respaldo, con el tipo de la property: lo que se le asigna se convierte como en cualquier asignación (field := 7 en una property long), y asignarle otro tipo es un error de compilación (#547, V7). 

public property nivel: long
  set(v)
    field := v * 2             // guarda el doble
  endset
endprop

Una subclase puede redeclarar una property de su padre: es una redefinición —sus accesores son virtuales y la hija trae su propio campo de respaldo—, así que el código del padre que la lee ve la de la hija. Vale igual con un padre del mismo módulo que de otro (#529, V7).

Properties sync (thread-safe)

public class Account
  public sync property balance: integer
  public function Account(initial: integer)
    this.balance := initial
  end Account
end Account

El modificador sync antes de property envuelve el getter y setter auto-generados con lock() / unlock() contra un Mutex compartido por instancia. El compilador:

  • Declara automáticamente un field oculto __syncMutex (heredado por subclases — sólo se declara una vez en el primer eslabón de la jerarquía que necesita sync).
  • Lo inicializa con Mutex() al entrar al constructor. Si la clase no tiene constructor propio, le da los suyos, como con los inicializadores: uno por cada sobrecarga del constructor del padre, con sus mismos parámetros (que pasa con super(...)), o uno sin argumentos si el padre no tiene.
  • Inserta this.__syncMutex.lock() al inicio y this.__syncMutex.unlock() al final de cada getX/setX.

Garantías: cada acceso individual al backing field es atómico respecto a otros threads. Una lectura nunca devuelve un estado parcial; una escritura es indivisible.

Importante: una expresión compuesta como this.value := this.value + 1 NO es atómica como un todo — se descompone en get + add + set, cada uno atómico individualmente, pero entre ellos otro thread puede colarse. Para operaciones atómicas compuestas usa un Mutex explícito alrededor del bloque.

Un return dentro del cuerpo custom de get/set sync libera correctamente el mutex: el emisor inyecta el unlock antes del salto al punto de salida (no hace falta try/finally explícito en BP). Y una excepción que salga del cuerpo —un throw o un error dentro de una función a la que llama— también lo suelta antes de seguir su camino (V7). Lo mismo aplica a sync properties a nivel módulo.

Properties a nivel módulo

module Counter
  // Property pública del módulo. El estado vive en un global
  // privado, accesible desde fuera SÓLO a través del get/set.
  public property tick: integer
  public function bump()
    tick := tick + 1
  end bump
end Counter

module App
  import Counter
  function main(arg: string)
    Counter.bump()
    print Counter.tick           // lectura cross-module → 1
    Counter.tick := 42          // escritura cross-module
  end main
end App

BP permite declarar property también fuera de una clase, a nivel módulo. Es la forma canónica de exponer estado mutable a otros módulos: las var de módulo son privadas por diseño (no se exportan en la interfaz), pero una public property expone su getter/setter sintéticos, accesibles vía Modulo.nombre desde otro módulo que la importe.

Internamente el compilador emite:

  • Un global privado __prop_<nombre> que es el backing field.
  • Una función pública __prop_get_<nombre>() que devuelve el valor.
  • Una función pública __prop_set_<nombre>(__val) que lo escribe.
  • En la interfaz, una línea prop <nombre>:<tipo> public que viaja a los módulos importadores (sin exponer los accesores como funciones normales).

El identificador tick dentro del propio módulo resuelve al getter/setter (no al global directo), así que la encapsulación se respeta también dentro del módulo dueño. Una property de módulo lleva su valor inicial igual que una var a nivel módulo (ver §5.1): un literal queda grabado en el módulo, y cualquier otra expresión se calcula al cargarlo, antes de la función inicializadora del módulo.

sync también es válido en properties de módulo: 

module Stats
  public sync property contador: integer
end Stats

En este caso el módulo declara un único Mutex global (__prop_mutex) compartido por todas sus sync properties. Se inicializa al cargar el módulo (en __init) y el get/set envuelven su cuerpo con lock/unlock. Las garantías y limitaciones son las mismas que para sync en clases.

Limitaciones del MVP:

  • No se soportan properties owner a nivel módulo (sólo en clases).
  • No se soporta final a nivel módulo (el modificador sólo aplica a properties de clase).

9.6 Miembros estáticos / final

En BP no hay keyword static: un miembro es estático cuando se declara con el nombre cualificado por la clase (Clase.miembro) dentro del cuerpo de la clase. Vale para const, var, property y function: 

public class Counter
  public const Counter.MAX: integer := 100   // const estática
  var Counter.viva: integer                   // var estática (privada, como todo campo)

  public property Counter.total: integer     // property estática (get/set auto;
                                               // admite get/set custom con `field`)

  public function Counter.bump()               // método estático
    Counter.total := Counter.total + 1
  end Counter.bump
end Counter

// Acceso SIEMPRE cualificado, sin instancia — también desde métodos
// de instancia:
Counter.total := 7
Counter.total += 3
Counter.bump()

El estado estático vive como global del módulo dueño (uno por clase, no por instancia); los tipos de 8 bytes (long/double) funcionan igual. final en clase: no extensible; en método: no overridable (el modificador va antes de function o class).

Los miembros estáticos cruzan la frontera del módulo (desde V7): Lib.Counter.total := 3, Lib.Counter.total += 1 y Lib.Counter.bump() valen desde otro módulo igual que desde el propio, y una hija de otro módulo ve los estáticos protegidos de su base. Las const estáticas viajaban ya. Lo único que no llama a un estático es una función native (§8.3).

La var estática no cruza — y no es una limitación, es el modelo. Una var (de módulo o de clase) vive en el segmento de datos del módulo, y ese segmento sólo es válido para el código del propio módulo. Por eso ninguna var puede ser public: el estado sale del módulo únicamente por getters y setters. Si un descendiente de otro módulo necesita ese dato, declara una property (protegida, sin public): cruza por sus accesores igual que la property de módulo. Los campos de instancia son el caso aparte: cruzan por ranura porque el hijo es el objeto.

9.7 Fields owner

public class Caja
  var owner contenido: Recurso
  public function Caja(r: Recurso)
    this.contenido := r
  end Caja
end Caja

Cuando una Caja se destruye —la libere quien la libere: su dueño, el GC o el final del programa—, su campo owner contenido se destruye y se libera también, antes que ella y recursivamente (§9.4b). Al reasignar el campo, el valor anterior se destruye antes de escribir el nuevo.

10. Módulos

10.0 El módulo raíz: Core

Core es el módulo del sistema (la unidad System de Turbo Pascal), escrito en BasicPlus y compilado como raíz: sus funciones públicas se ven sin cualificar en todo programa, importe Core o no — strlen, abs, parseInt, now, newIntArray… Están declaradas en bpstdlib/Core.bp, una por línea, como funciones con cuerpo inline (§8.3b), y ese fichero es la única fuente de la tabla de primitivas de las dos máquinas virtuales: Builtin.java y builtin_ids.h se generan de él.

import Core es implícito. El compilador lo añade al árbol de todo módulo que no lo escriba (salvo en el propio Core): se puede indicar o omitir, y el resultado es el mismo. Sus clases (List, Exception, Integer…) se escriben sin cualificar, y las cuatro del lenguaje —Object, Thread, Mutex, StringBuilder— son clases BasicPlus de Core.bp: hasta V7 el compilador las escribía en Java y copiaba las cuatro en cada .mod (≈1,3 KB por módulo, usara hilos o no); ahora se compilan una vez y cada módulo las referencia. El orden de sus campos y métodos es un contrato con las dos VMs (Thread.run() en la ranura 0, el tid en el campo 0…) y está anotado en el propio fichero. Por eso redeclarar una de las cuatro en otro módulo es un error de compilación: «'Thread' es una clase del lenguaje (Core): no se puede redeclarar».

Una intrínseca es una función normal, y se sobrecarga como cualquier otra: Math.sign(x: integer) y Math.sign(x: float) son dos funciones con el mismo nombre (hasta V7 la segunda se llamaba signF), y len son dos sobrecargas de la raíz — len(s: string) y len(a: any[]) — en vez de un caso especial del compilador. any[] («un array de lo que sea», cualquier T[] encaja) sólo puede escribirse en Core, como any. Sobre una clase no hay azúcar: la longitud de una List es lista.length().

  • function main(arg: string) es el entry-point. Sólo se llama al main del módulo raíz; los mains de las dependencias quedan como utilidad para testing standalone.
  • El argumento se pasa desde la consola del IDE con run MiApp hola (comillas opcionales si lleva espacios) y en las dos VMs de PC como segundo posicional (java -jar bpgenvm.jar MiApp.mod hola, bpgenvm-c MiApp.mod hola).   import Util                       // misma library
  import com.example.Util           // path cualificado
  import ext.tools.Helper from "plugins/helper.mod"
  ...
end App
  • El último segmento del path es el alias local (Util, Helper). Lo usas como Util.foo().
  • from "<path>" dice al compilador dónde encontrar el .mod (o el .bp) del que sacar la interfaz. En ejecución la VM busca el módulo por su nombre, siempre en el mismo orden: el pack en ejecución, la carpeta del programa (/app), la biblioteca estándar (/lib) y la zona de packs — la ruta del from no se usa.
  • import Core no hace falta (desde V7): el compilador lo añade a todo módulo (§10.0), así que los tipos de Core —List, Integer/Long/Float/Double/Boolean, Comparable, Exception, RuntimeError— y try/catch o throw (§11) se usan sin escribirlo. Escribirlo no cambia nada.
  • Los imports no son transitivos (Core aparte, que va siempre). Importar A no trae los módulos que A importa: para nombrar un tipo de B hay que importar B («tipo cualificado 'B.Y' no encontrado»), y también si lo que usas de A depende de B. El compilador lo dice según el caso:
    • una firma de A (de una función o de un método) usa un enum de B: es un error, aunque no uses esa firma — «la firma de 'A.f' usa el enum 'B.E' y este módulo no importa 'B' (un enum no puede cruzar sin resolver): añade `import B`»;
    • una clase de A extiende una de B: es un aviso —«base cross-module 'B.Y' de la clase importada 'A.X' no resuelta (¿falta el import de su módulo?) — sin sus miembros heredados»— y la clase se usa sin lo que hereda de B: llamar a un miembro heredado es un error («'X' no tiene miembro de instancia 'm'»);
    • una clase tuya extiende una de B sin importarlo: es un error — «la clase 'Z' extiende 'B.Y' y este modulo no importa 'B': anade `import B` (los imports no son transitivos)».
  • Una librería puede crecer sin recompilar a quien la usa (desde V7, el enlace tardío): un .mod lleva sus referencias a las clases de otros módulos por nombre y firma, y el cargador las resuelve contra la versión que encuentra. Un método, un campo o una property añadidos —o reordenados— no rompen a nadie, como en Java; lo que sí rompería —quitar un miembro, cambiar su firma o su tipo— se rechaza al cargar, nombrando el símbolo: «'Usa' necesita 'Lib.Sensor.nombre()s' y 'Lib' (gen 0) no lo tiene (tiene 'nombre()i'): recompila 'Usa'». Y una dependencia más antigua que la versión contra la que se compiló el módulo tampoco carga: «'Lib' (gen 2) es mas antiguo que el que 'Usa' necesita (gen 3): actualiza /lib o recompila» (la versión de una librería, su gen, es la clave version de su .bpbuild).
  • Qué cruza la frontera del módulo (desde V7): todo lo que un descendiente o un cliente pueden nombrar — funciones, clases con sus métodos, properties y campos públicos y protegidos, todas las sobrecargas del constructor (super(...) elige por firma), los miembros estáticos (§9.6), consts y properties de módulo. Lo private no cruza — tampoco dentro del módulo.

10.4 module interface — RETIRADO

BasicPlus no tiene interfaces. Ni para clases —que sería lo defendible— ni para módulos. Las secciones que aquí describían module interface, implements y el binding import Contrato:Impl se retiran del lenguaje (decisión de Eduardo, 30-ago-2026), junto con los ejemplos que las usaban.

Lo que aquellas tres secciones perseguían —evolucionar un módulo sin romper a quien lo usaba— sigue siendo un objetivo, y la forma prevista es la herencia entre módulos: dejar el módulo original y añadir otro que herede de él. Está en suspenso a propósito, porque para que funcione hace falta un control de versiones efectivo que hoy no existe. Se retomará entonces. Una parte ya está: desde V7, una librería puede crecer —añadir métodos, campos o properties— sin recompilar a quien la usa (§10.3).

Para componer funcionalidad hoy: import normal (§10.3) y herencia entre clases (§9), que sí existe y se usa —la biblioteca estándar tiene 38 casos, de SyncList extends Core.List a RuntimeError extends Exception.

10.5 Encapsulación clase ↔ módulo

Desde dentro de una clase, sólo se accede a símbolos públicos del módulo (functions, consts, vars, properties). Tipos (clases, enums, namespaces de imports) siempre visibles. 

module M
  function helperPriv(): integer     // privado
    return 99
  end helperPriv

  class C
    public function bad(): integer
      return helperPriv()             // ERROR: no es public
    end bad
  end C
end M

10.6 Dos pasadas: por qué los módulos pueden llamarse entre sí

El compilador procesa cada módulo dos veces:

  1. Pasada de interfaz — recorre las declaraciones y anota qué expone el módulo: firmas de funciones, clases, properties y constantes públicas. No mira el cuerpo de las funciones.
  2. Pasada completa — ya con las interfaces de todos los módulos disponibles, compila el código de verdad y resuelve cada llamada.

Esa separación es la que permite que dos módulos se llamen mutuamente. Cuando se compila el cuerpo de Par, la interfaz de Impar ya existe (y al revés), así que ninguno de los dos tiene que estar terminado para que el otro compile:

module Par
  import Impar
  public function esPar(n: integer): boolean
    if n == 0 then return true
    return Impar.esImpar(n - 1)   // llama a Impar
  end esPar
end Par

module Impar
  import Par
  public function esImpar(n: integer): boolean
    if n == 0 then return false
    return Par.esPar(n - 1)       // ...y Par llama a Impar
  end esImpar
end Impar

Esto compila y funciona. La circularidad en el CÓDIGO está permitida, y vale igual para funciones, para métodos de clase y para properties.

El límite: las DEFINICIONES no pueden ser circulares

Lo que no puede cerrar el círculo es el tipo en sí. Si una clase pública de TA expone un tipo de TB, y la clase de TB expone a su vez un tipo de TA, la interfaz no se puede construir: para saber qué es TA.Nodo hay que saber antes qué es TB.Hoja, y viceversa.

// TA.bp
public class Nodo
  public property vecino: TB.Hoja      // TA depende de TB...
end Nodo

// TB.bp
public class Hoja
  public property duenyo: TA.Nodo     // ...y TB de TA -> circulo cerrado
end Hoja

El compilador no aborta: avisa y deja fuera de la interfaz el miembro que no puede resolver.

-- omitidas en interfaz (1): class Hoja.property duenyo: tipo no exportable

Ojo con este aviso. El módulo compila, pero esa property no existe para quien lo importe: el error real aparecerá más tarde, en el módulo que intente usarla. Si ves un «no expone X» que no encaja con lo que has escrito, mira si hay un ciclo entre definiciones.

Cómo romperlo, en orden de preferencia:

  • Un tercer módulo con los tipos comunes, que importen los dos. Es la solución limpia y la que suele revelar que esos tipos eran una pieza aparte desde el principio.
  • Invertir una de las dos dependencias: normalmente una de las dos direcciones es la natural y la otra se puede resolver pasando el dato como parámetro en vez de guardarlo como campo.
  • Juntar las dos clases en un módulo, si de verdad son una sola cosa partida en dos ficheros.

Recuerda que el límite es sólo para tipos que cruzan la frontera del módulo. Dentro de un mismo módulo, dos clases pueden referirse la una a la otra sin problema.

try
  riskyOp()
catch e: RuntimeError
  print "runtime: " + e.msg
catch e: MiError
  print "mi error: " + e.detalle
catch e
  print "desconocido"
finally
  print "limpieza"
endtry

throw RuntimeError("algo fallo")
  • try establece un handler en una pila de handlers de la VM.
  • catch e: Foo sólo atrapa instancias asignables a Foo. catch e (sin tipo) es catch e: Exception: atrapa cualquier excepción y e tiene su msg. Va siempre la última (las cláusulas se prueban en orden).
  • finally se ejecuta siempre (con o sin excepción) —también cuando un return, break o continue sale del try—. Y no puede salir él con return, break ni continue (error de compilación): taparía la excepción que fuera en vuelo. Un throw dentro sí vale, y un break a un bucle de dentro del finally, también.
  • El catch es opcional: un try … finally … endtry, sólo con la limpieza, también vale (V7). Si salta una excepción, el finally corre y ella sigue su camino hacia el try de fuera.
  • throw expr lanza el valor. Si es una clase, su class_ptr se usa para el match de catch tipado.
  • Todas las excepciones descienden de Exception (con su property msg), que vive en el módulo raíz Core junto a RuntimeError; como Core se importa siempre (§10.0), se usan sin escribir nada.
  • print e imprime el mensaje: Exception.toString() devuelve msg y lo heredan RuntimeError y las excepciones de usuario.
  • Una excepción de usuario es una clase que extiende Exception (hereda msg; añade los campos que quieras). throw y el catch tipado exigen clases que desciendan de Exception.
  • Los errores nativos de la VM (división por cero, referencia nula, índice fuera de rango, fallos en funciones native...) se lanzan como RuntimeError y se cazan igual, da igual el módulo donde ocurran.
  • El texto de fuera que no es UTF-8 válido (fromBytes, readFile, readLine…) lanza EncodingError, hija de RuntimeError (V8, §4.1): quien ya atrapa RuntimeError la atrapa también, y catch e: EncodingError delante la trata aparte.
  • Quedarse sin memoria también se atrapa. Si una reserva no cabe en el heap, la VM lanza un RuntimeError con el mensaje No space in heap en vez de morir: un programa que trabaje al límite puede liberar y reintentar, o al menos dejar constancia antes de rendirse. Igual en el PC que en el micro.

  procesarLoteGrande()

  print "no ha cabido: " + e.msg
endtry
  • Una excepción que nadie atrapa en el thread main termina el programa con código de salida 1 (igual en las dos VMs y en placa); en otro thread acaba ese thread, los demás siguen, y al final el programa sale igualmente con 1 (§14.1). El informe es diagnóstico, no salida del programa, y el IDE lo recoge en su consola (help error lista los códigos); pero las dos VMs no lo dan igual. La VM-C —la de las placas— nombra la clase de la excepción y su mensaje, la lance el programa o la propia VM (excepcion no atrapada: Core.RuntimeError: División por cero, … MiMod.MiError: …). La VM Java, con un throw del programa, también nombra la clase (Excepción no atrapada: MiMod.MiError: …) y añade un stack trace con el nombre simbólico y la línea de cada frame; pero con un error de la propia VM —división por cero, índice fuera de rango…— sólo da el mensaje ("División por cero"), sin la clase ni el stack trace.

12. Owner semantics

BP soporta destrucción determinística de objetos en complemento al GC tradicional. La regla básica: un objeto puede tener un propietario; al morir el propietario, el objeto poseído muere también (cascada). Y morir es destruirse: corre su destructor (§9.4b) y después se libera su memoria.

12.1 var owner x: T

  • Al asignar x := y, el anterior valor de x se destruye antes.
  • Al salir de scope —fin normal, return o excepción—, se destruye el valor actual de x.
  • Asignar x a una variable no-owner copia la ref sin transferir propiedad (sigue siendo de x).
  • Asignar a otra variable owner local transfiere: la fuente queda a null sin destruirse.
  • Un var owner local no escapa: ni se devuelve ni se guarda en un campo o en un array (error de compilación, §5.3).

12.2 Fields owner

var owner f: T dentro de una clase. El descriptor de la clase marca qué campos son owner; al destruir la instancia, cada uno se destruye antes que ella, del último al primero (en su destructor, la instancia ya los tiene a null). Al reasignar el campo, el valor anterior se destruye antes de escribir el nuevo (asignación owner-safe).

12.3 Cascada por arrays de refs

Si un campo owner contiene una referencia a un array TYPE_ARRAY_REF, sus elementos también son del objeto: al destruirse el contenedor se destruyen todos los no nulos del array, cada uno con su destructor. Esta es la mecánica que sustenta OwnerList.

14. Concurrencia

Los threads BP los ejecutan N workers (hilos reales del SO) que se reparten los threads encolados. En el PC, por defecto N=1, y el SMP es opt-in: --workers=N en la VM Java (ver §16.2) y --smp=N en la VM-C de PC. En la placa, desde V7, las de dos núcleos —la Pico 2, la Metro, la ESP32-S3 y la ESP32-P4— ejecutan dos threads del programa a la vez de verdad, uno por núcleo (cada uno en un run, una tarea del sistema); las demás —la C3, la C5, la C6 y las STM32—, uno cada vez. En las de dos núcleos, las claves vm.runs y vm.cores del ENV lo cambian sin regrabar (guía del IDE §9.3); lo que supone para el programa, en §14.6.

14.1 Modelo de ejecución

  • El thread BP main (tid 0) arranca primero: ejecuta el initializer del módulo y luego main(arg). Tiene stack grande (16 KB). Sólo él puede ejecutar la instrucción HALT que apaga la VM.
  • Cualquier subclase de Thread añade un thread BP nuevo al hacer start(). La VM le asigna la pila que pide su constructor —Thread(stackSize), en bytes; con 0, 2 KB— y lo encola RUNNABLE. Un worker Java libre lo coge y ejecuta su run() hasta retorno (THREAD_EXIT) o yield()/sleep()/join()/lock.
  • La pila tiene un tope, y se vigila. Cada función, al entrar, comprueba que lo suyo cabe en la pila de su thread; si no —una recursión sin fin, o una pila pequeña para lo que hace—, lanza un RuntimeError «desbordamiento de pila (el hilo tiene N B)», que se atrapa con try como cualquier otro, igual en las dos VMs. Los demás threads no se enteran.
  • Una excepción que nadie atrapa acaba su thread: los demás siguen, y al final el programa sale con error (código 1), para que el IDE o un script no lo den por bueno. Si es el main, se acaba el programa. Y lo dice en ese momento, en la salida del programa (la consola del PC, la del IDE con la placa): === excepcion no atrapada en un hilo (el hilo termina): <mensaje> ===.
  • No hay tope de threads vivos (desde V7): lo pone la memoria, porque cada uno se lleva la pila que pide. Un thread terminado deja su sitio a otro, así que a lo largo de su vida un programa puede crear todos los que quiera. start() lanza RuntimeError si no queda memoria para la pila que pide («no hay memoria para la pila del hilo»).
  • Cada thread BP tiene su propio contexto (ThreadContext): PC, SP, BP, CS, región de stack, pila de handlers de excepción. El heap (incluyendo objetos owned por threads) es compartido.
  • Cuando todos los threads BP terminan, la VM se apaga. Si main hace HALT antes, los workers en vuelo se cortan en su próximo opcode.
  • La interfaz gráfica corre en un thread BP propio: Gui.start() lo arranca y vuelve, Gui.run() además espera. Está en el volumen de gráficos.

14.2 Preempción y yield()

El quantum se cuenta en opcodes, igual en las dos VMs: 1024 por defecto, ajustable con quantum=N en el ENV de la placa (--quantum=N en el PC). Al agotarlo, el worker re-encola el thread y coge el siguiente RUNNABLE; así el reparto entre threads cae en las mismas instrucciones en la VM Java y en la VM-C (antes la Java usaba un temporizador de 10 ms, y el orden de la salida cambiaba de una ejecución a otra). La VM-C cede además el turno al sistema, y así un stop del IDE llega aunque el programa no duerma.

En paralelo a la preempción, el código BP puede ceder CPU cooperativamente:

  • yield() — cede una vez; el thread sigue RUNNABLE y el scheduler lo elige cuando le toque.
  • sleep(ms) — marca BLOCKED_SLEEP hasta now() + ms. Si no hay otro RUNNABLE, el worker Java duerme hasta el próximo wake-up.
  • join() sobre otro thread — marca BLOCKED_JOIN hasta que el target termine.
  • Mutex.lock() sobre un mutex tomado — marca BLOCKED_MUTEX hasta hand-off.

14.3 Encapsulación de cuerpos de case

El cuerpo de cada case dentro de un parallel es el run() de una subclase anónima de Thread sintetizada por el compilador. Sigue la misma regla de encapsulación de objeto que un método de clase normal: no puede leer/escribir variables globales del módulo. Sí puede llamar funciones del módulo, instanciar clases, usar consts y llamar builtins.

Para coordinarse, los threads usan objetos compartidos (Mutex, List, clases con estado) en vez de globals mutables. El compilador rechaza la lectura directa con mensaje: 

error semántico: el cuerpo de un 'case' dentro de 'parallel' no puede
acceder a la variable global 'X'; usa una const, una función o un
objeto compartido

El bloque default NO sufre esta restricción: corre en el thread llamador y ve sus locales y globals.

14.4 GC y concurrencia

El GC mark-and-sweep es conservativo: escanea los stacks de todos los threads vivos y los data blocks de los módulos para identificar roots. Las operaciones de heap (heapAlloc, gc(), freeOwnedObject) están serializadas bajo vmLock — dos workers no pueden mutar el heap a la vez.

Safepoint stop-the-world: cuando un worker necesita GC (porque heapAlloc agota el heap), pone una bandera global stopTheWorld. Los demás workers la chequean al inicio de cada iteración del intérprete: sincronizan tc.{pc,sp,bp,cs} y abandonan runOnContext con señal YIELD. Vuelven a la WorkerLoop, ven la bandera y parquean en vmLock.wait(). El worker que pidió GC espera a que ninguno otro esté en estado RUNNING (los que están parqueados en vmLock.wait dentro de heapAlloc se cuentan como parqueados vía parkedInHeapAlloc), corre gcLocked, y luego limpia la bandera.

Además, cada tc mantiene una ancla de alloc (tc.allocAnchor): heapAlloc deja en ella el ref recién alocado antes de soltar vmLock. Si otro worker dispara GC entre el return de heapAlloc y el push posterior del caller, el escáner del GC ve la ancla como un root extra y no libera el objeto en tránsito.

El GC no mueve nada: lo libre puede acabar repartido en huecos. Heap.compact() sí mueve —desliza lo vivo al principio del heap, con el mundo parado—, pero sólo a petición del programa y en condiciones controladas: desde Main, sin otros hilos vivos y nunca desde una native (referencia §13.19). Es posible porque una referencia es un handle: mover un objeto es cambiar su entrada de la tabla.

Wraps de opcodes de alocación: NEW_OBJECT y las variantes de NEWARRAY mantienen vmLock desde la alocación hasta la publicación al stack BP (tc.sp sincronizado). Esto cierra la ventana en que otro worker podría sweepear el objeto recién creado antes de que su ref llegue al stack de quien lo creó.

La carrera B1 del SMP de la VM Java (dos workers sobre el mismo contexto de thread) no está cerrada: con más de un worker (--workers), la VM Java sigue siendo experimental, como desde V2. Se han cerrado dos caminos suyos —en V6, el que se veía (sólo decide sobre un thread el worker que lo posee); en V7, el de un sleep(0) (#613)—, pero no está demostrado que no tenga más. La VM-C no la tiene (su planificador no reclama un thread que aún tiene dueño), y desde V6 su Mutex es atómico. synctest.bp, synclisttest.bp y modpropsync.bp son las pruebas de referencia. En el PC el SMP sigue siendo opt-in (un worker por defecto); en la placa, la VM-C usa los dos núcleos donde los hay (§14.6).

14.5 print con varios threads

Un print sale entero: su línea, con todas sus piezas y el salto, no se mezcla con la de otro thread. Entre dos print seguidos sí puede caer la línea de otro: 

print "Resultado=", r      // sale junta: nada se cuela entre "Resultado=" y r
print a
print b                   // entre a y b puede salir la línea de otro thread

Una línea que se arma con varios print acabados en ; (§2) también sale entera: lo que dejan en la línea abierta sale junto, con el salto.

Para que varias líneas salgan juntas, júntalas en un StringBuilder e imprímelas con un solo print: 

var sb: StringBuilder := StringBuilder()
sb.appendStr("Temperatura: " + t + "\n")
sb.appendStr("Humedad: " + h)
print sb.toString()

Vale en todas las placas y con cualquier número de workers: con uno, el cambio de turno podía caer en mitad de un print; con dos, dos threads imprimen de verdad a la vez. El límite: una línea de más de 1 KB (lo que cabe de una vez en la cola de salida de la placa más pequeña) puede salir en trozos. Y una traza que la VM escribe mientras se calcula una pieza (en el PC, las de los periféricos simulados: [gpio] read pin=25 …) sale antes que la línea, no en medio.

14.6 Dos núcleos: lo compartido y el fallo fatal

En una placa de dos núcleos (la Pico 2, la Metro, la S3 y la P4), dos threads del programa ejecutan a la vez, cada uno en su núcleo. No cambia nada que no fuera cierto con uno —el cambio de turno también puede caer entre dos lecturas—, pero ahora pasa de verdad, y más a menudo. La regla es ésta: la memoria que comparten dos threads es cosa del programa; la de la VM, de la VM. Lo que dos threads leen y escriben a la vez —un campo de un objeto compartido, una lista, una property— se protege con un Mutex o con una property sync. Sin él, el resultado es el de cualquier carrera —un contador que pierde sumas, una lista a medio cambiar—, pero la VM no se rompe: su heap, sus tablas y el GC están protegidos, y un print sale entero (§14.5). La GUI se protege sola: cada operación sobre sus widgets la ejecuta el mismo run, así que se pueden tocar desde cualquier thread.

Lo que se gana depende del programa y de la placa: dos threads que calculan a la vez van más rápido, hasta el doble (medido: ×2 en la P4, ×1,55–1,68 en la Pico 2, ×1,13 en la Metro); con cadenas, poco o nada (×1,33 en la P4; en la Pico 2, ×0,83: pierde); y un programa de un solo thread no gana nada (§17). Un programa que se depura, o que usa SQLite, va con un run aunque haya dos. Las cifras, y cómo volver a un núcleo sin regrabar, en la guía del IDE §9.3.

Un fallo fatal. Un error del programa es una excepción (§11): se atrapa o, como mucho, acaba su thread. Un fallo fatal es otra cosa: el sistema de la placa ya no puede seguir —un HardFault, la memoria del sistema agotada, una comprobación interna que falla—. En la Pico 2 y la Metro, con dos núcleos, la placa deja el informe en el log —en una RAM que sobrevive al reinicio—, se reinicia sola en medio segundo y, al arrancar, lo dice (Machine.resetCause() y el INFO del IDE dan «fallo fatal») y no lanza el autorun: un programa que fallara nada más arrancar sería un bucle de reinicios; desde el IDE se arranca a mano. Las ESP32 hacen lo mismo con el autorun: tras un pánico (una excepción del procesador) o el perro guardián de las interrupciones, la placa se reinicia y el arranque siguiente no lo lanza y lo dice en el log y en la consola (Machine.resetCause() da panic/exception o int-watchdog). El perro guardián de tareas, el que arma el módulo Wdt, no es un fallo fatal: tras él, el autorun sí se lanza. En las STM32, un HardFault deja el informe en el log y la placa parada. Que el fallo de un run no tumbe la placa entera es de V8.

15. Eventos

Un evento permite que un objeto avise de que algo ha pasado sin saber quién le escucha. El que emite declara la firma de lo que va a notificar; el que escucha se suscribe con un método suyo.

Es la base de la interfaz gráfica —un botón no sabe qué hace tu programa cuando lo pulsan—, pero no está limitado a ella: sirve en cualquier clase.

15.1 Declarar y disparar

Dentro de la clase que emite, event declara nombre y parámetros. Admite valores por defecto como cualquier firma:

class Boton
  public property numero: integer
  event onClick(sender: Boton, veces: integer := 1)

  public function Boton(n: integer)
    this.numero := n
  end Boton

  public function pulsa(n: integer)
    raise onClick(this, n)      // dispara
  end pulsa
end Boton

15.2 Escuchar: function event y ::

El que escucha declara un manejador con function event y la misma lista de parámetros. No hace falta que sea público — lo normal es que sea privado, porque nadie más lo llama.

La suscripción se escribe con ::, que ata un objeto y un método suyo:

class Panel
  var nombre: string

  public function Panel(n: string)
    this.nombre := n
  end Panel

  function event pulsado(b: Boton, veces: integer)
    print("  handler: boton " + b.numero + " x" + veces + " en " + this.nombre)
  end pulsado
end Panel

var b: Boton := Boton(7)
var p: Panel := Panel("principal")
b.onClick := p::pulsado          // suscribe el metodo de ESE objeto

15.3 Lo importante: raise NO llama al manejador

Esto es lo que hay que tener claro para no llevarse sorpresas: raise encola el evento y vuelve inmediatamente. El manejador se ejecuta después, cuando el planificador le inyecta el frame al hilo entre dos cortes de ejecución.

print("antes del raise")
b.pulsa(3)
print("despues del raise (el handler todavia NO ha corrido)")
sleep(30)
print("fin")

Sale, en este orden:

antes del raise
despues del raise (el handler todavia NO ha corrido)
  handler: boton 7 x3 en principal
fin

Dos consecuencias prácticas:

  • Quien dispara no se bloquea. Por eso un botón puede avisar sin que la interfaz se quede parada esperando a tu código.
  • No cuentes con que el manejador ya haya corrido en la línea siguiente al raise. Si necesitas el resultado, pásalo por el propio evento o espera a que el manejador lo deje escrito.
  • El manejador es una función más de su hilo: puede ceder (sleep, un Mutex ocupado, un join) y lanzar. Una excepción que no atrape acaba ese hilo, como cualquier otra, y la salida lo dice (§14.1). En la GUI los manejadores corren en el hilo de la GUI: si uno lanza sin atraparla, la pantalla deja de responder, y la salida dice por qué.

15.4 Llamadas asíncronas

El mismo :: sirve para lanzar un método en otro hilo, sin escribir una clase Thread a mano:

Thread(obj::metodo(args)).start()

Está pensado justo para lo que bloquea: una lectura larga, un cálculo pesado o un acceso a disco lanzados desde un manejador de la interfaz, para que la pantalla siga respondiendo mientras tanto.

Y aquí sí hay que tener cuidado. Lo que se lanza así corre en un hilo distinto del principal. Si vas a compartir variables con el resto del programa, usa los mecanismos de sincronización del lenguaje (ver 14. Concurrencia) para evitar corromper los datos. Un manejador de evento normal no tiene este problema: corre en el hilo que lo recibe.
